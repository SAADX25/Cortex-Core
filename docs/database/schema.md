# Database and provenance

`202610070001_foundation.sql` creates common parts/manufacturers, field-level source records, five category-specific specification tables and separate M.2 slot rows. NULL means unknown, not zero or assumed support. Category-specific composite foreign keys prevent a CPU specification row referencing a motherboard. Positive/enum/slug/confidence constraints protect the database boundary; the Zod import boundary adds full specification/provenance validation.

`catalog_records` projects the normalized rows into the TypeScript contract. It is security-invoker, so parent and child RLS are evaluated as the calling role. Timestamps use explicit UTC ISO strings. Public SELECT policies require the owning part to be public; no INSERT/UPDATE/DELETE grants or policies are provided to anonymous/authenticated clients. Manufacturers are public metadata. The initial roles intentionally have no private account access.

Every real non-null specification leaf must have a provenance key such as `specs.socket` or `specs.m2Slots.0.key`: source URL, source organization, verified/retrieved timestamp, verified/unverified status and confidence. Fixture provenance is explicitly labeled and may omit an external URL. A production importer must validate using `catalogSchema`, write transactionally under privileged server credentials, keep new records private, and publish only after review. Database SQL by itself does not enforce complete per-field provenance; imported data and reads are runtime-validated. Source arrays use stable ordered projections so indexed provenance paths remain deterministic.

The development seed is generated from the validated TypeScript fixture dataset with `node tools/data-import/generate-seed.mjs`. It is isolated in `supabase/seed/development.sql`, creates public fictional records for local use only and is intentionally not a production import. `pnpm data:validate INPUT.json [OUTPUT.json]` validates untrusted import files without scraping or writing to a database.

PGlite unit tests execute this migration and seed in PostgreSQL and check source/category/capacity constraints, schema round trips, write denial and invisible private parents/children for both API roles. `supabase/tests/security.sql` provides additional pgTAP grant/RLS checks for `supabase test db` in an actual Supabase environment. Hosted PostgREST, Storage and authentication integration require provisioning and remain untested locally.

Assets should be uploaded to a dedicated Supabase Storage bucket under SHA-256 names. Reviewed public assets may use a public read bucket; private assets need private buckets, object policies and signed URLs. No bucket or write policy is exposed by this milestone. Supabase is an adapter: tables, views, migration SQL and the repository interface remain portable PostgreSQL/domain contracts.
