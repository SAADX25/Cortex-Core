## Dashboard and resource bounds

CPU, NVIDIA/AMD/Intel GPU, board, physical storage and DIMM readings remain separate source records. Integration class, disk form factor and exact My PC device identity are not guessed. Values are Celsius with original source IDs/names and availability. Last observation is receipt time, not an acquisition timestamp. Unavailable sensors never become zero-degree readings.

One SVG chart shows one selected source sensor; no chart library, WebGL context or animation loop is added. Ranges: 1, 5, 15, 30, 60 minutes. History accepts only fresh available observations, ignores repeated/out-of-order cache timestamps and splits lines at missing readings or gaps over 15 seconds. Previously valid historical observations remain history even when current readings go stale. Buffers are session-only: 64 series, 721 points/series, 12,000 total points, maximum age 60 minutes. Limits apply together and can shorten retention; omission is explained on screen. Disconnect, lifecycle pause, navigation/unmount and reconnect clear history. Terminal errors leave prior history with a gap until explicit disconnect/reconnect. Accessible SVG summaries and a bounded observation table accompany the chart.

Warnings default off and have configurable category thresholds. They use only fresh, finite, available temperatures in the accepted range; missing, stale, ambiguous, unsupported or future-dated readings do not warn. Defaults are display preferences, not manufacturer limits. No hardware protection, automatic shutdown, OS notification, device control, fan control, voltage control, overclocking or firmware action exists.

Only Monitoring owns the poller. My PC/3D have no thermal subscriptions or polling. The ordinary specification scan still restores SQLite cache and makes one startup scan, plus explicit rescans. Device arrays remain stable when unchanged. Existing demand-rendered 3D resources and teardown are untouched. Dashboard rendering occurs on actions, bounded polling completion and the freshness deadline; disconnected Monitoring has no periodic timer. Current sensor rows are capped at 128 per category, warning text at 64 entries, and chart table at 20 rows; extra records are explained rather than silently assigned values.

## Future providers — design only

Keep provider selection/session ownership in Rust, with independently packaged providers behind a read-only protocol. A future provider interface should expose version/capability negotiation, explicit start of selected read categories, bounded snapshot reads, cancellation, stop and health. It must never accept URLs, arbitrary executable paths, control commands or arbitrary register/device selectors from React. Library/driver code stays outside the Rust host. A packaged helper is a separate proposed transport, not an HTTP isolation workaround. Process separation does not prevent a whole-system driver/hardware freeze.

| Future capability   | Required contract and validation                                                                                                                                                                                |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CPU/GPU utilization | Explicit percent units, acquisition timestamp, observation timestamp, category-specific availability, independently tested read-only source. Missing data stays unknown.                                        |
| CPU/GPU clocks      | Explicit frequency units and sensor scope (core/package/memory). No inference from marketing frequency, no frequency changes.                                                                                   |
| Fan RPM             | Read-only speed plus source identity; absence does not mean a stopped fan. No fan curve or PWM commands.                                                                                                        |
| SSD SMART health    | Drive identity and typed attributes, provenance, units and interpretation version. No invented health percentage, SMART writes or self-tests. Isolate and separately validate any storage command provider.     |
| GPU power           | Watts, sensor scope and true acquisition freshness; no power-limit access.                                                                                                                                      |
| History             | Bounded per-provider buffers, explicit gaps, no inferred samples. Persistent history/export would require separate retention/privacy choices and schema versioning.                                             |
| Notifications       | Explicit opt-in, fresh readings only, hysteresis/debounce and rate bounds; stale/missing values clear conditions. On-screen thresholds are not emergency protection. OS notifications are not implemented here. |

Candidate evaluation remains [the source/license comparison](external-temperature-sources.md): externally managed LHM first; an independently packaged .NET LibreHardwareMonitorLib helper only after a separate-machine safety gate; smartmontools as a storage-only candidate with GPL obligations; HWiNFO SDK only with explicit applicable commercial/redistribution rights; older OHM has insufficient maintenance evidence for new cross-PC integration. None of these future providers is integrated or executed. LHM's [upstream documentation](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) describes broad sensor classes, not universal compatibility. Home Assistant's [HTTP integration](https://www.home-assistant.io/integrations/libre_hardware_monitor/) is a protocol-model reference, not permission to enable remote access. [Mozilla's MPL FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/) and [release-specific third-party notices](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/v0.9.6/THIRD-PARTY-NOTICES.txt) must be considered before copying/distributing covered software; no such software was copied here.

Before any helper integration/execution: pin exact artifacts, audit licenses/notices/source and relinking obligations, establish provenance and executable authenticity, select an authenticated local transport, limit privileges, prohibit arbitrary command execution/control surfaces, bound messages/work/time/memory, preserve category isolation and quarantine, and test on independent Intel/AMD + NVIDIA/AMD/Intel configurations including storage/DIMMs, absent sensors, lifecycle, permissions, shutdown/restart and sleep/resume. Future helper consent must remain separate from external HTTP consent. No helper is authorized for this development PC.
