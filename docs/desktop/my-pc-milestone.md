# My PC milestone — October 8, 2026

Cortex Core now opens around locally detected Windows hardware. Main navigation is My PC, 3D View and Settings. Assembly/catalog routes fall back to My PC; installation, replacement, destination, occupied-slot, saved-build and reset controls are absent from the primary UI. Existing build domain, compatibility, catalog, asset pipeline, database security and their tests remain available in isolated code.

## Native source mapping

The scanner uses Rust `wmi` 0.18.4 over Windows COM and `windows` 0.62.2. It does not launch PowerShell, CIM shell tools or subprocesses. All WQL projections are fixed in `apps/desktop/src-tauri/src/hardware.rs`; neither command accepts a query, path or script from React.

## Startup, data and privacy

`load_hardware_scan` restores the last normalized successful snapshot from the app-local `hardware.sqlite3`. `scan_hardware` performs fixed queries on a blocking worker, separate from the window/UI thread. A native mutex serializes requests across webview reloads; the frontend also deduplicates startup and concurrent rescan clicks. No timer or periodic polling is installed.

The native schema is versioned and typed (`Hardware`, `Device`); only normalized names/category properties are returned. The frontend validates schema, bounds, category property allowlists and numerical totals before rendering. Unknown, blank and malformed provider values become `Unknown` / `Not reported by system`. Device ordering is normalized; unchanged successful scans retain their device arrays and update only the last-scanned time. Invalid caches do not block a fresh scan. Total failure retains the last successful snapshot; a partial scan updates available categories and shows unavailable categories without failing the dashboard.

No serial numbers, CPU identifiers, PNP IDs, MAC addresses, Windows keys, user names or computer names are queried. Device/computer name is deliberately omitted for this milestone. Cache and diagnostic paths are fixed by Tauri. Diagnostics contain reviewed unavailable-category/failure codes and cache status, with no raw WMI error/value payloads. Hardware scanning never accesses Supabase or remote services.

## Dashboard and visualization

Six large cards present CPU, GPU, Memory, Motherboard, Storage and Operating System. Details disclose each processor/adapter/module/disk; motherboard details include firmware. The inspector traps focus as a native HTML dialog, closes with Escape and restores the invoking control. Rescan Hardware and Copy Specifications work from My PC. The copied report includes all detected devices and firmware.

3D View loads separately. The retained React Three Fiber renderer uses demand rendering, adaptive DPR/antialias/shadow quality, board LOD and automatic declarative geometry/material cleanup. Generic device shapes are generated from the detected CPU/GPU/module/disk records. Each shape and accessible component button opens its detected device inspector. Orbit drags do not trigger component selection. Renderer loading/context failure preserves usable detected component inspection. Native fullscreen/Escape remain available.

The screen states: “Generic visualization — specifications are from your detected hardware.” The generic board is a procedural visual descriptor from the existing template infrastructure; its fictional catalog specifications are never shown as detected values. No exact product model, socket, motherboard form factor, DIMM/PCIe population order or physical disk enclosure is inferred. Storage uses generic drive shapes; NVMe bus alone does not prove M.2 form factor. Integrated and discrete adapters are listed independently but their physical placement/type is not inferred.

## Known detection limitations

- Windows firmware and driver providers can omit fields, return placeholders, or present devices exposed by virtualization, RAID or Storage Spaces. Windows disk devices are distinguished from partitions; controller abstractions may hide individual underlying drives.
- WMI `AdapterRAM` is deliberately ignored because it is a 32-bit field. DXGI dedicated memory is driver-reported, may differ from marketed nominal capacity, and excludes shared system memory. Zero, mismatched names and duplicate adapter descriptions stay unknown.
- Disk media enrichment requires a unique model+size match; similar drives, renamed devices and provider discrepancies can leave media unknown. Bus metadata remains exactly what Windows reports; SCSI/RAID is never relabeled as NVMe.
- Configured RAM speed and generation depend on SMBIOS support. Memory total can be available even if module information is not.
- CPU maximum clock is the WMI/firmware value, not a measured frequency or a guaranteed advertised boost clock. CPU socket is not inferred.
- Firmware version is reported without asserting legacy BIOS versus UEFI boot mode.
- WMI queries run off the UI thread but depend on provider responsiveness; this milestone does not forcibly cancel a hung COM provider. The last cached dashboard remains usable while a scan runs.
- Exact-model retrieval, product database enrichment and Export Report are future work. No sensor monitoring, continuous polling or assembly editor is included.
